# Voult — Feature Roadmap and Security Issues

**Audit date:** 2026-10-11<br>
**Scope:** `apps/client`, `apps/server`, `apps/server/migration`, `apps/extension`, `packages/vault-core`, `launcher`
**Review type:** source review and local build/test checks; not a penetration test or security certification.

**Status:** `[x]` implemented and wired at the stated scope · `[~]` partial · `[ ]` not implemented.
**Priority:** **P0** resolve before a public security-sensitive release; direct confidentiality, account-security, or credential-disclosure risk · **P1** required before calling the password-manager experience production-ready · **P2** maturity, platform, and operational improvements.

## Feature Roadmap

### Implemented

- [x] Vault-centric identity and account creation: client-generated vault UUID, password signup/login, and cookie session (`apps/client/src/lib/auth/flows/signup.ts`, `flows/login.ts`; `apps/server/src/endpoints/register.rs`, `auth.rs`).
- [x] Client-side v2 encryption: PBKDF2-HMAC-SHA256 → HKDF-separated auth/wrapping keys → random vault key → AES-GCM vault/envelope encryption; server vault handlers transport ciphertext (`packages/vault-core/src/crypto.ts`, `apps/server/src/endpoints/get_vault.rs`, `update_vault.rs`). **The current KDF strength remains a security issue below.**
- [x] Web vault experience: create/open/import flow, item add/edit/delete, search, selection, and password masking (`apps/client/src/app`, `apps/client/src/lib/vault`). New vaults are created **empty** — no seeded demo entries (`apps/client/src/lib/auth/flows/signup.ts`).
- [x] Local-first CRUD and sync engine: encrypted SQLite-WASM/OPFS intents, optimistic updates, deterministic merge/quarantine, bounded CAS retries, and server compare-and-swap (`apps/client/src/lib/sqlite/web`, `apps/client/src/lib/sync`, `packages/vault-core/src/merge.ts`, `apps/server/src/endpoints/update_vault.rs`).
- [x] Per-vault local isolation: OPFS file names include the validated vault UUID, IndexedDB device records use `vault:<id>`, and teardown closes/clears only the active vault’s scoped state (`apps/client/src/lib/sqlite/web/init-db.ts`, `lib/crypto/device-key.ts`, `lib/auth/teardown.ts`).
- [x] Web inactivity lock and configurable timeout; extension inactivity/screen-lock handling; shared server `lock_epoch` for cross-surface lock convergence (`apps/client/src/lib/auth/use-autolock.ts`, `lib/auth/lock.ts`, `apps/server/src/endpoints/lock.rs`, `apps/extension/src/background/vault.ts`). Locking is local-first: keys are wiped before `/lock` is attempted. The idle deadline is persisted per surface and evaluated on restart, so closing the app does not reset the timer; the extension records its own durable activity/lock state.
- [x] MV3 extension MVP: one-time pairing or web-session discovery, password unlock/device unlock, origin-based suggestions, explicit fill, save/update prompts, and SSO sign-in markers (`apps/extension/src`, `apps/server/src/endpoints/pair.rs`).
- [x] Google OAuth and encrypted Voult-package creation/import, including server-side Drive transport and revision-aware replacement primitives (`apps/client/src/lib/google`, `lib/vault/import.ts`, `apps/server/src/google`, `endpoints/google_endpoints.rs`). Ongoing Drive refresh is handled by post-commit server-side mirroring rather than a client sync path; see the mirroring entry below.
- [x] Shared Zod vault/intent schemas and merge/origin helpers are used by both client and extension (`packages/vault-core/src`).
- [x] Foundational server controls: session-derived vault authorization, session renewal at authentication, transactional registration, explicit configured CORS origins, atomic version CAS, and `Cache-Control: no-store` on `/api/*` (`apps/server/src/session_auth.rs`, `src/endpoints`, `src/main.rs`). These do not replace the open hardening items below.

### Partial or planned

- [ ] **P1 — Automatic sync and recovery UX (partial):** local intent-created sync works and the manual path exists; focus/reconnect sync hook is not mounted (`apps/client/src/lib/sync/use-sync-triggers.ts` is not used by `_layout.tsx`). Surface pending, failed, and quarantined intents and offer retry/recovery.
- [x] Provider-neutral cloud backup with Google Drive and Dropbox implementations: OAuth, encrypted package backup/restore, and provider CAS transport (`apps/server/src/cloud/providers/`), plus **post-commit out-of-band mirroring**. The server remains the write authority; providers are disaster-recovery copies only. The mirror re-serializes stored ciphertext and refuses rather than clobbering a changed remote revision. It never blocks `/update_vault`; outages and conflicts are recorded on `cloud_binding`. Every binding state write is conditional on `binding_generation`, so a provider switch mid-upload cannot stamp a stale revision or status onto the new binding, and a provider switch is refused (`409 BACKUP_IN_PROGRESS`) while a mirror holds the vault. Dropbox uses App folder storage and revision-conditional uploads. OAuth credentials remain plaintext in SQLite; token-at-rest protection remains a follow-up.
- [ ] **P1 — Password change and key rotation (partial):** server endpoint `/vault/password` changes verifier and optionally KDF metadata (`apps/server/src/endpoints/update_vault_password.rs`), but no client rewrap/atomic recovery flow or user-facing password-change UI is wired.
- [ ] **P1 — Visible web logout and session/device lifecycle (partial):** server and extension logout paths exist; the web client deliberately has **no user-facing logout**, because the selected vault is the app's identity and switching/creating is the supported way to change it. Session loss (`SESSION_REQUIRED`) is an authorization fact only: it marks `serverSession: "missing"` but keeps an unlocked vault open and usable locally (sync pauses), retains a locked vault's real lock reason, and always keeps the selection and local device key. Settings → Security exposes **"Forget this device"** to revoke that device key. Still missing: a server-side session/device inventory and revoke-all flow.
- [ ] **P1 — Release-ready browser extension (partial):** the MV3 build and MVP flows work, but origin fallback, permission review, broader browser testing, and store/release validation remain (see Security issues).
- [ ] **P1 — Recovery and portable backup (partial):** **paper recovery key shipped.** Every vault is created with a 160-bit recovery secret that can reopen it with no device key and no remembered master password (`packages/vault-core/src/crypto.ts`, `apps/server/src/endpoints/recovery.rs`). The secret is issued as a one-page **PDF recovery file**, offered once behind a mandatory interstitial and can only be rotated from Settings, never replayed; `/recover` and rotation both read that file and there is no typed-key fallback. The artifact is an owned format (`packages/vault-core/src/recovery-pdf.ts`, writer + reader, no PDF dependency) verified against poppler and Ghostscript. **Creation order is the load-bearing part:** `POST /register` runs *after* the file is saved (`lib/vault/registration.ts`), so a row cannot exist without the user already holding the file that opens it — a reload mid-flow leaves nothing behind, and a failed commit re-registers the same vault id and key so the saved PDF is never orphaned. **Known limitation:** the file is the *sole* copy of the key, so a user who deletes it can no longer rotate (`regenerate` demands proof of the current key) and recovery falls back to a fresh vault. A session-authenticated "issue a new recovery file without proof" path would fix that, but it silently revokes the owner's existing copy from anyone holding a stolen session, so it is a real trade-off rather than a bug to patch. Still missing: general-purpose encrypted export/import-and-restore, recovery when the vault row is absent from the server (case 4 — the ciphertext then lives only in a provider `VoultPackage`, which now carries the vault's `recoveryEnvelope` so a restore keeps the original recovery key), and any device-key-loss route (cases 1–2, where `unlockWithDevice` 401s on a dead cookie before touching local material).
- [ ] **P1 — Password generator, password health, TOTP/passkeys, and richer item fields/history:** not implemented as complete user-facing features.
- [ ] **P1 — Vault format/KDF migrations:** `VAULT_DOCUMENT_FORMAT_VERSION` exists, but there is no tested migration framework for evolving item formats or KDF profiles.
- [ ] **P1 — Native parity:** Keychain/Keystore-backed keys, native database, biometrics, and lifecycle/screenshot protections are not implemented; the supported product is web plus Chrome extension.
- [ ] **P1 — Accessibility and localization:** systematic keyboard/screen-reader, focus, contrast, reduced-motion, and localization coverage remains.
- [ ] **P2 — Multi-user/shared vaults and secure sharing:** no encrypted sharing/revocation protocol, expiring sharing links, or family/team vaults.
- [ ] **P2 — History, recycle bin, activity/recovery tooling, and privacy-preserving opt-in telemetry:** not implemented.
- [ ] **P2 — Production operations:** release signing/provenance, dependency/SBOM governance, incident response, restore drills, and independent security review are incomplete.

## Security issues

### Completed controls (limited to verified implementation)

- [x] Master password and vault plaintext are processed client-side; server vault handlers store/return ciphertext and metadata, not decrypted vault contents (`packages/vault-core/src/crypto.ts`, `apps/server/src/endpoints/get_vault.rs`, `update_vault.rs`). This does not protect against same-origin script compromise or a malicious replacement web bundle.
- [x] Vault keys are imported as non-exportable `CryptoKey`s; AES-GCM uses generated 96-bit IVs; password and auth key derivations use distinct HKDF labels (`packages/vault-core/src/crypto.ts`).
- [x] Session cookie is HttpOnly; authentication renews the session; vault reads/writes derive the vault ID from the session; CORS uses an explicit origin list (`apps/server/src/main.rs`, `session_auth.rs`, `endpoints`).
- [x] Version-checked vault writes are atomic and return conflict on stale versions (`apps/server/src/endpoints/update_vault.rs`).
- [x] Web/extension lock can converge through a monotonically increasing server lock epoch; API responses are marked `no-store`; COOP/COEP headers needed by SQLite WASM are configured (`apps/server/src/main.rs`, `endpoints/lock.rs`, `apps/client/public/_headers`).
- [x] Favicon proxy requires an authenticated session and implements URL/size/timeout/image checks plus private-IP checks for the initial host (`apps/server/src/endpoints/favicon.rs`). Redirect/DNS rebinding gaps remain below.
- [x] New vaults are created **empty**: the encrypted document is written with `items: []` and no call site can seed entries, so no demo credential (`test@example.com` / `password`) ever reaches a real user's vault (`apps/client/src/lib/auth/flows/signup.ts`, `apps/client/src/lib/vault/create.ts`).
- [x] Local validation run: `packages/vault-core` tests **100/100 pass** (incl. recovery known-answer vectors cross-checked against `node:crypto`, and the recovery-PDF format verified against poppler `pdfinfo`/`pdftotext` and against Ghostscript — a file re-produced by a foreign PDF writer still parses); `cargo test` **78 server tests** across cloud provider/mirror, favicon, `/update_vault`, vault creation, and the full recovery flow (challenge/unlock/rewrap/regenerate) including per-IP throttling, challenge expiry/capping, uniform failure responses, and the rewrap column-discipline and Rule-R1 invariants; client and extension `npx tsc --noEmit` pass. The recovery flow was additionally exercised end-to-end with real client crypto against a live server (register → recover → rotate), confirming client/server agreement on the HMAC labels. These are not end-to-end or security test suites; the provider HTTP calls are not covered by a mock-transport test, and the recovery UI — including the new file picker and download/print — has **not** been exercised in a browser.

### Open issues — fix before public release

- [ ] **P0 — Strengthen password KDF and add a migration profile.** `packages/vault-core/src/crypto.ts` still uses PBKDF2-SHA256 with 60,000 iterations and has no separately versioned KDF profile or benchmark-backed upgrade path. This materially weakens resistance to offline guessing after ciphertext/verifier theft. Evaluate a reviewed memory-hard KDF or materially stronger calibrated profile; migrate by client-side rewrapping without sending password/key material to the server.
- [ ] **P0 — Remove the reusable verifier as a directly replayable login credential.** `apps/server/src/endpoints/auth.rs` compares `vault_verifier` with ordinary string equality; anyone who obtains the DB verifier can replay it to establish a session. Prefer a reviewed PAKE; if retaining the verifier protocol, store only a salted verifier hash, compare safely, and treat the value as a credential rather than harmless metadata.
- [x] **P0 — Rate-limit authentication and pre-auth endpoints.** Implemented in `apps/server/src/rate_limit.rs` as DB-backed fixed-window budgets shared by every worker and every instance over the same SQLite file: `/auth` 30/min/IP + 10/10 min per vault (cleared by a correct verifier, so only the owner can reset it), `/register` 5/h/IP + 30/h global, `/get_crypto_params` 60/min/IP, vault writes 60/min per session vault, vault admin 10/h, `/pair/consume` 20/min/IP plus a durable per-code attempt column, and `/recovery/{challenge,unlock,rewrap}` 10–20/min/IP. Refusals are `429` + `Retry-After` + the existing `{error_msg, code}` envelope; the client and extension treat them as retryable, never as a wrong password or a lost session. Per-IP budgets key on the socket peer and honour `X-Forwarded-For` only from `TRUSTED_PROXY_IPS`, because `realip_remote_addr()` is client-spoofable. Limits are per database: N instances over N databases still get N budgets, and a single-process in-memory limiter is not a security boundary for a multi-instance deployment. Residual, documented: an attacker who knows a vault id can refuse fresh `/auth` for up to 10 minutes at a time, and rate limiting does not make a weak master password safe (see the KDF item). Server tests cover budgets, reset-on-success, unknown-vault parity, header spoofing, the shared store across instances, and the fail-closed extractor.
- [ ] **P0 — Fix extension origin fallback before broad distribution.** `packages/vault-core/src/origin.ts` calls a last-two-label comparison “registrable suffix” matching. This is not public-suffix aware: unrelated sites such as `bank.co.uk` and an attacker-controlled `other.co.uk` can be treated as a weaker match. Replace with a reviewed Public Suffix List implementation or remove the fallback; add adversarial tests for multi-label suffixes, IDNs, ports, and schemes. A weaker rank does not by itself make a wrong fill safe.
- [ ] **P0 — Sanitize HTTP/access logs and OAuth redirect errors.** `apps/server/src/main.rs` uses `Logger::default()`, whose default request-line format includes query strings. OAuth callback `code`/`state`, pending state, vault IDs, and favicon URLs can therefore enter logs; OAuth handler logs/redirects also include provider email or error detail (`apps/server/src/endpoints/google_endpoints.rs`). Log path templates/status only, redact sensitive query parameters, and return fixed user-facing error codes.
- [ ] **P0 — Enforce request/protocol bounds at every write boundary.** Registration, vault creation/update, and password metadata handlers accept weakly validated values: arbitrary KDF iteration counts, crypto versions, salt/envelope pairings, IV/base64 lengths, and ciphertext sizes. **Partially addressed:** both vault-creation endpoints (`/register`, `/vaults`) now require the full password and recovery envelope sets and reject blanks before opening a transaction, and body-deserialization failures return the documented `INVALID_INPUT` envelope rather than a bare 400 (`apps/server/src/endpoints/mod.rs`). `/recovery/rewrap` and `/recovery/regenerate` validate canonical UUIDs, exact base64 lengths, and a bounded KDF count before any DB mutation. Still open: `/auth`, `/update_vault`, `/vault/password`, ciphertext size caps, and any cross-instance body limit.
- [ ] **P0 — Add security-focused automated tests before release.** Current coverage is 50 shared-core schema/merge/origin tests, 3 favicon unit tests, and the new rate-limit unit/HTTP tests (`rate_limit.rs`, `auth.rs`, `get_crypto_params.rs`, `register.rs`, `update_vault.rs`, `pair.rs`). There are still no client crypto/auth/sync integration tests or server auth/session/CSRF/input-limit/CAS/migration integration tests. Add KDF vectors, wrong-password/tamper/downgrade, auth/session, cross-vault isolation, lost-response/conflict, and server-boundary tests; make them release gates.
- [ ] **P0 — Ship restrictive web security headers and gate debug tooling.** Only COOP/COEP and API `no-store` are present; CSP, HSTS (for HTTPS deployments), `nosniff`, frame restrictions, and restrictive referrer/permissions policies are absent (`apps/server/src/main.rs`, `apps/client/public/_headers`). The Expo debug route is part of the app route tree (`apps/client/src/app/debug`). Establish a tested production CSP/header policy, gate or remove debug UI from release bundles, and test the built artifact for source maps, unexpected network access, and secret exposure.

### Open issues — production hardening

- [ ] **P1 — Encrypt or eliminate persisted cloud credentials.** `cloud_token` and `cloud_pending_token` store access/refresh tokens directly in SQLite (`apps/server/src/entity/cloud_token.rs`, `cloud_pending_token.rs`, migration). These are sensitive provider credentials even though vault data is encrypted, and continuous cloud mirroring puts them on the hot path for every vault write. Protect them with OS-backed/server-managed encryption at rest, least-privilege file access, expiry/deletion policy, and redacted backups/logs.
- [ ] **P1 — Enforce transport and cookie invariants for any network deployment.** The server currently binds `localhost`, but `SESSION_COOKIE_SECURE` defaults to `false`; `SameSite=None` can be selected without enforcing `Secure` (`apps/server/src/main.rs`). Fail closed for non-loopback/public deployment without TLS and Secure cookies, validate `SameSite=None`/Secure combinations, and document reverse-proxy trust. Do not claim a remote production deployment based on loopback defaults.
- [ ] **P1 — Add CSRF/origin checks and session revocation semantics.** CORS is allowlisted, but state-changing cookie-authenticated routes do not validate Origin/Fetch Metadata or a CSRF token. Cookie sessions are stateless; current-session purge does not revoke a copied cookie server-side, there is no absolute lifetime, and high-risk actions have no reauthentication/device revocation (`apps/server/src/main.rs`, `session_auth.rs`).
- [ ] **P1 — Remove account enumeration and timing differences.** `GET /get_crypto_params` returns `404 VAULT_NOT_FOUND` for unknown IDs (`apps/server/src/endpoints/get_crypto_params.rs`); generic `/auth` errors help but do not conceal this pre-auth distinction. Use a non-enumerating response and consistent work where practical.
- [ ] **P1 — Complete password-change protocol atomically.** `/vault/password` can replace verifier/salt/iterations without receiving a new password-wrapped vault-key envelope or proving client rewrap completed. It is not currently wired to a client flow, but enabling it as-is can strand existing encrypted data or desynchronize credentials. Require reauth and client-side rewrap with an atomic, recoverable update; add failure/race tests.
- [ ] **P1 — Prevent favicon-proxy SSRF on every redirect and connection.** `apps/server/src/endpoints/favicon.rs` checks DNS/IP for the initial URL, then lets `reqwest` follow redirects without revalidating each target; the separate DNS check is also subject to resolution/connect TOCTOU. Re-check and pin public destinations for every hop or use an egress policy that blocks private/reserved networks.
- [ ] **P1 — Clear secrets and redact client errors.** Signup/login component state and vault forms need an explicit lifecycle review; lock clears Zustand keys/data but not every local form/search/selection buffer or OS clipboard. Error logging includes raw client errors (`apps/client/src/app/auth/signup.tsx`, `app/home/index.tsx`, `lib/sync/index.ts`), which may carry request configuration. Clear password inputs on success/failure and lock, purge sensitive form/cache state, define clipboard expiry behavior, and log only sanitized error codes.
- [ ] **P1 — Verify backup, database, and migration safety.** The database file has no code-enforced permission/encryption/backup policy; migrations have no CI upgrade/restore coverage, and SQLite foreign-key enforcement is not verified by a test (`apps/server/src/config.rs`, `src/db.rs`, `apps/server/migration/src`). Define private file permissions, encrypted backups, retention/deletion, tested restore, and migration behavior on existing installs.
- [ ] **P1 — Add server rollback protection or document the limit.** CAS prevents concurrent overwrites, not a malicious/compromised server replaying an older valid ciphertext snapshot. Define the trust guarantee and decide whether client-held monotonic checkpoints/history are required.
- [ ] **P1 — Complete extension release review.** Content scripts match all HTTPS sites and inspect login forms; this is core to autofill but high-impact (`apps/extension/src/manifest.json`, `src/content/content.ts`). Review permission minimization, explicit user-consent UX, save/fill phishing cases, `http` warnings, store privacy disclosures, and manual browser matrix before distribution; automated extension security tests are absent.
- [ ] **P2 — Add crypto-context binding and document memory limits (partially addressed).** AES-GCM had no associated data binding vault ID/version/envelope purpose; raw temporary key bytes cannot be reliably zeroized in JavaScript and WebCrypto non-exportability does not defend against same-origin XSS/devtools. **The recovery envelope is now AAD-bound** to its vault (`utf8("voult-env|v2|" + vaultId + "|recovery")`), closing the transplant hole that a second envelope type would otherwise have opened. Still open: the password and device envelopes carry no AAD, and the zeroization/XSS limits above are undocumented.
- [ ] **P2 — Dependency/release governance and operational response.** Lockfiles exist, but automated vulnerability/license/secret scanning, SBOM, reproducible/signed release provenance, incident response, key rotation, and restore drills are not demonstrated. Add CI and operational ownership before wider deployment.

> **Release gate:** do not describe Voult as production-ready until all P0s are closed, the production bundle and extension have been reviewed, no credentials or plaintext can enter logs/build artifacts, and the target deployment enforces its documented transport/session/storage controls.

**Changelog:** 2026-10-29 (rate limits) — Closed the P0 rate-limit item with a DB-backed limiter (`apps/server/src/rate_limit.rs`, table `rate_limit`, migration `m20261028_000008_rate_limit`). One atomic `INSERT … ON CONFLICT … RETURNING` per charge keeps a fixed window in SQLite, so every Actix worker and every instance sharing the database spends one budget — the previous `ChallengeThrottle`/pair throttles were per process, and their IP key (`realip_remote_addr()`) was client-spoofable via `X-Forwarded-For`. `/auth` now has 30/min/IP plus 10/10 min per supplied vault id (unknown and known vaults counted identically; cleared only by a correct verifier), `/register` 5/h/IP + 30/h global, `/get_crypto_params` 60/min/IP, vault writes 60/min per session vault, `/recovery/{challenge,unlock,rewrap}` 10–20/min/IP, `/pair/consume` 20/min/IP with the attempt counter moved from an unbounded process map to `pair_code.attempts`. Refusals are `429` + `Retry-After` + `{error_msg, code}`; the web client schedules one bounded retry (intents stay durable) and the lock screen distinguishes throttling from a wrong password, the extension treats 429 as transient. Extractors are polled concurrently by Actix, so the limiter guarantees the handler never runs rather than the body never being parsed (documented in the plan). `cargo test` 126/126, client/extension typechecks pass; live smoke verified every budget, `/lock` and reads unaffected, and that `rate_limit` stores only hashes. Residual: a known vault id can deny fresh `/auth` for 10 minutes at a time, and N instances over N databases still get N budgets. Plan: [`plans/p0-auth-rate-limits.md`](plans/p0-auth-rate-limits.md).

**Changelog:** 2026-10-27 (manual-only lock propagation) — Corrected cross-surface coupling found in testing: idle/timer locks are now local to their surface and no longer call `POST /lock`; only a deliberate manual lock bumps the shared `lock_epoch`. Previously the extension's 5-minute timer published every idle lock, each bump made the web record a durable `peer` lock, and the web reopened locked regardless of its own timer. Screen-lock is treated as a local timer event; the extension's explicit Lock button, and the web's Lock Voult, remain global. The lock screen now states why it is locked and offers **Unlock with this device** for `autolock` locks (manual/peer remain password-only). A one-time `voult.lockPolicyVersion` migration discards a legacy `peer` record produced by the old propagation. No schema, crypto, or wire-contract change.

Guarded `sync()` (which now pins on the *selection*, since M2 made `session` nullable while a vault stays selected), `adoptServerSnapshot`, the vault-open and cloud-import flows, home's async decrypt effect, and `useGetVault`'s version write. Confirmed a pending OAuth token never becomes a selection and that the extension remains keyed on server-session identity. No extension changes: it already derives vault identity and `lock_epoch` from the cookie and must not take web's navigation state.
