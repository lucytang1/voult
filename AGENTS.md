# AGENTS.md

Password manager (voult): Expo web client + Actix-Web API server, both zero-knowledge (server only ever sees vault ciphertext, salt, iterations, `vault_verifier` HMAC (stored only as a salted HMAC, `apps/server/src/credentials.rs`), and wrapped vault-key envelopes — never master password, vault key, or plaintext).

Vault is the only identity. There is no `user`/`email` table — `vault.id` is a client-generated UUID (`apps/client/src/lib/crypto/index.web.ts:38`) used as session principal (`apps/server/src/session_auth.rs:6`).

## Layout

- `apps/client` — Expo (SDK 55) web app. Entry: `expo-router`. State: Zustand (`src/lib/state`) + TanStack Query (`src/lib/queries/http.ts:13` `withCredentials:true`). Local DB is SQLite WASM with OPFS **per-vault** (`src/lib/sqlite/web/init-db.ts:15` → `file:voult-<vaultId>.db`). Device key + envelope are per-vault in IndexedDB `voult` (`src/lib/crypto/device-key.ts:11` key `vault:<vaultId>`). Styling: NativeWind/Tailwind v4.
- `apps/server` — Rust crate named **`pass-manager`** (not "server"). Actix-Web 4 + SeaORM (SQLite). Single vault-centric migration `m20260901_000001_vault_centric_init` creates `vault`, `session` (unused — cookie store used), `google_token`, `cloud_binding`, `oauth_state`, `google_pending_token`. Cargo workspace root includes `migration`.
- `apps/server/migration` — SeaORM migration crate; see its README for CLI usage.
- `crates/logger` — shared Rust logger (default `logger` instance / `Logger::create(ServerContext::… | LauncherContext::…)`) used by the server and launcher. It writes UTC, context-tagged lines to stderr and installs the global `log` backend, so Actix, SeaORM/SQLx, and other dependency logs use the same filter and formatter.
- `launcher` — standalone macOS tray app that spawns the server binary from `../apps/server`.

## Commands

Client (run in `apps/client`):
```sh
npm install            # runs patch-package via postinstall — patches in patches/ must apply
npm run sync:sqlite-web   # REQUIRED before web export; copies sqlite-wasm assets into public/sqlite
npm run build:web      # exports to dist/ (clears EXPO_PUBLIC_API_URL so it uses same-origin /api)
npx tsc --noEmit       # typecheck; there is no lint/test script
npm run web            # dev server on :8081
```

Server (run in `apps/server`):
```sh
cargo run              # binds localhost:8080, serves API under /api and client's exported site at /
```

Logger tests (run in `crates/logger`):
```sh
cargo test
```

Env / config (`apps/server/src/main.rs:38`): all vars optional with per-install defaults. `DATABASE_URL` defaults to `~/Library/Application Support/Voult/voult.db` (`sqlite://…?mode=rwc`, `resolve_database_url()`). `SESSION_COOKIE_KEY` defaults to per-install `~/Library/Application Support/Voult/session.key` (0600, 64 random bytes base64, `resolve_session_cookie_key()`); if provided must be ≥64 chars else ignored with warn, and panics only if resolved key <64. `STATIC_DIR` defaults to probing `Resources/dist` (Voult.app bundle) then `../client/dist`. Optional: `CORS_ORIGINS` (comma-separated; defaults `http://localhost:8081` + `127.0.0.1:8081`), `SESSION_COOKIE_SECURE`/`SAME_SITE`/`TTL_SECONDS` (default 7d idle), `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (+ `GOOGLE_REDIRECT_URI`) for Drive sync. `.env` is loaded from CWD, then `Resources/.env`/`google.env`, then `~/Library/Application Support/Voult/.env` (`load_bundled_env()`). `VOULT_LOG_LEVEL` (`debug|log|warn|error`, default `log`, `info` aliases `log`) is read by `crates/logger` and controls all server and launcher logging, including records arriving through the `log` facade. `RUST_LOG` is ignored.

## Gotchas

- Logging is unified: `crates/logger` is both the first-party API and the global `log` backend. `VOULT_LOG_LEVEL` controls everything; `RUST_LOG` is ignored. Do not initialize `env_logger` or install another `log` backend. Contexts are typed: `ServerContext` for the server/migration and `LauncherContext` for the launcher; each logging module declares `const LOG: logger::ServerLogger` / `LauncherLogger`. Dependency records use their `log` target as the context.
- Build order for a full local run: `npm run build:web` in `apps/client` first, then `cargo run` in `apps/server` (it serves `../client/dist`; warns and serves API-only if missing).
- New Git worktrees do not inherit gitignored `.env` files. Run `./scripts/env-worktrees.sh setup` once per clone; `.githooks/post-checkout` then symlinks every ignored `.env`/`.env.*` from the main checkout into new worktrees. If a tool bypasses hooks (or uses `git worktree add --no-checkout`), run `./scripts/env-worktrees.sh sync --all`.
- The server runs migrations automatically on startup (`Migrator::up` in `main.rs:222`); you don't need to invoke them manually for normal dev.
- COOP/COEP headers are required by sqlite-wasm OPFS (`SharedArrayBuffer`) — set both on the server responses (`main.rs:280` `DefaultHeaders`) and in `public/_headers`. Don't remove them.
- Server never handles plaintext: crypto (v2 hierarchy: PBKDF2-HMAC-SHA256 → HKDF `auth`/`vault-wrap-v2` → random 256-bit vault key AES-GCM, device key wrap) lives entirely client-side in `src/lib/crypto/index.web.ts:10` and `src/lib/crypto/device-key.ts`. Cookie `voult_session` stores only `vault_id` (`session_auth.rs:6`), never keys/envelopes.
- Client storage is **per-vault namespaced** (`apps/client/architecture.md#local-storage-namespacing`): one OPFS file per vault, one IndexedDB record per vault (`vault:<id>`). SQLite is opened only once a vault key is in hand (`initSQLite(vaultId)` validates UUID) and closed on lock. Session loss is centralized in `src/lib/auth/teardown.ts` and is triggered by the 401 interceptor (`src/lib/queries/http.ts`) and the session-sync hook. It only marks `serverSession: "missing"`: an **unlocked** vault keeps its key, plaintext, and open SQLite handle (local use continues; sync pauses), while a **locked** vault stays locked. It **retains** the vault selection and the local device key + envelope — an expired cookie is an authorization fact, not a change of identity and not a lock. `signOutOfVault()` is the separate, destructive path that does delete device material (Settings → Security → "Forget this device"); there is no routine logout.
- Site icons are cached in the **same IndexedDB database** (`lib/favicon`, store `favicons`, key `<vaultId>\n<iconUrl>`, 30-day TTL with a 6-hour negative cache) and read **synchronously** at render, so the list paints real icons instead of flashing the fallback glyph. The cache deliberately survives locking (display-only bytes, same class as the plaintext vault-name cache) and is purged on vault switch (memory) and sign-out (disk). Never cache icons in the browser HTTP cache: `/api/favicon` stays `no-store`, and the server keeps only a process-lifetime in-memory cache plus a `<link rel="icon">` discovery fallback (`apps/server/src/endpoints/favicon.rs`).
- Lock semantics: `lockVaultStorage` (`src/lib/state/index.ts`) wipes `vaultKey`/`decryptedVault`/`authKey` but keeps session + device envelope. Every lock (manual button, autolock, peer/extension lock) goes through the shared `lockVaultNow()` (`src/lib/auth/lock.ts`): capture the password-wrapped envelope from cache → **wipe keys + ciphertext caches, close SQLite, persist the lock reason, route to `/lock`** → then, **for a manual lock only**, best-effort `POST /lock` (bumps shared `lock_epoch` so peers converge on their next check) and a same-origin broadcast. Local locking never waits for the network. Idle/timer locks stay local because web and extension have independent timeouts. Unlock with password unwraps locally via `LockMetadata` (no network on wrong password).
- **A lock is a decision, not a flag.** `persistLockRecord(reason)` writes `{vaultId, reason, lockedAt}` to `localStorage` (`src/lib/state/selection-store.ts`), where `reason` is `manual | autolock | peer`. The restart policy is the pure `decideRestore()` (`src/lib/state/vault-state.ts`), called from the bootstrap (`_layout.tsx`): `manual`/`peer` hold until an explicit unlock; `autolock` permits device unlock once the window lapses; with no record, the persisted last-activity timestamp (`voult.lastActivity.<vaultId>`) is compared against the current timer so closing the app does not reset the idle window. Session expiry is **not** a lock reason. With autolock set to "Never" an ordinary restart restores **unlocked**; a deliberate manual lock still does not. `useAutolock()` (`src/lib/auth/use-autolock.ts`, mounted in `_layout.tsx`) locks on inactivity, persists the deadline (throttled), and re-checks on visibility/resume; a hidden tab records no activity, and the timeout is re-read every tick so settings changes apply without a reload. The extension mirrors the policy with its own separately configured timeout and durable `chrome.storage.local` activity/lock records.
- **Vault selection is the app identity.** `VaultState` (`src/lib/state/vault-state.ts`) is a discriminated union — `no_vault` | `locked(vaultId)` | `unlocked(vaultId, vaultKey)` — with the key carried *inside* it, so "unlocked without a key" is unconstructible. Server-session status (`unknown | active | missing`) is tracked **orthogonally** in `AppState`; never infer one from the other. Switching is atomic: `switchVaultOpen()` verifies the server authenticated the requested vault and commits selection + session + key + document + version in one store write. Anything async captures `captureSelectionEpoch()` before awaiting and re-checks before committing, so a late response can never land in a different vault (an id comparison is insufficient — A→B→A leaves the id unchanged). The shared `AuthState` label and the `isLocked`/`vaultKey` store fields are gone.
- **The vault name is a label, not identity.** `vaultId` stays the identity everywhere (storage, session, AAD, sync guards). The name lives inside the encrypted document (`DecryptedVault.name`), is chosen during onboarding between the password and recovery file, and is renamed with a durable `rename` intent merged as document-level LWW. A per-vault `localStorage` cache (`src/lib/vault/name.ts`) lets the lock screen and chooser render it before unlock; it is a label, never key material. Settings → Vault keeps the full UUID. The server never receives the name.
- **The vault document is `{ name, folders, items }`.** Every writer (client mutations, sync, the extension) must **spread the document** and change only its field — never rebuild `{ name, items }`, or it silently erases folders (and any future field). Use the shared `parseVaultDocument` / `serializeVaultDocument` in `@voult/vault-core`. Folders are flat and append-ordered; `deleteFolder` cascades to its items.
- Autolock preferences live in `localStorage` (`src/lib/settings/index.ts`), not SQLite, because the deadline must be readable while locked. The web timer is enforced by the client; the extension timer is stored but **not yet delivered** to the extension (it still reads `voult.lockTimeoutMinutes` from `chrome.storage.local`) — that needs a per-vault settings record on the server the extension pulls on its next session check.
- **Vault recovery (case 3).** Every vault carries a recovery file from creation — no enable step, no disabled state. It is a 160-bit CSPRNG secret, rendered `XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX` (Crockford base32, **no checksum** — AES-GCM authentication is the verifier) and issued as a **one-page PDF**, never as text on screen. Crypto lives in `packages/vault-core/src/crypto.ts`; the two HMAC labels (`recovery-verify-v1`, `recovery-proof-v1`) are a wire contract with the server and are pinned by known-answer tests cross-checked against `node:crypto`.
  - **The recovery artifact is an owned PDF format** (`packages/vault-core/src/recovery-pdf.ts`) — writer and reader, no PDF library, ~1.4 KB output. It is Courier-only (every glyph advances exactly 0.6 em, so line centring needs no font metrics), uncompressed content stream, and carries the payload **twice**: once as visible page text, once in Info `/Subject`. `parseRecoveryPdf` scans raw bytes, inflates every stream (`DecompressionStream`, trying both `deflate` and `deflate-raw`, and both with and without the framing EOL before `endstream`) — so a file re-saved or re-produced by another PDF writer still reads. Anything that still fails gets a uniform "this needs the original file" message; a print-out or a re-scanned page deliberately does **not** import. Tests check the output against poppler and against Ghostscript, which are skipped, not failed, when absent.
  - **A `vault` row must never exist unless its recovery file is already in the user's hands.** `POST /register` is therefore the LAST step of creation, not the first: `prepareVaultFlow` / `prepareSignupFlow` / the Drive-restore path all produce a `PendingVaultRegistration` (`lib/vault/registration.ts`) that is entirely local, and `commitVaultRegistration()` is called only from the interstitial's Continue. Registration used to happen first and the file second, which meant a reload in between left a vault that opens with the master password but whose recovery path could never be repaired — `recovery/regenerate` demands proof of the key that was never saved. Three consequences to preserve: (1) a failed commit must keep the pending object so a retry re-registers the *same* vault id and key, or the PDF already on disk is orphaned; (2) if the commit succeeded but local setup failed, retry must skip `/register` rather than get `VAULT_EXISTS` (the `committed` state in both create screens); (3) the interstitial's copy — "Nothing has been uploaded yet" — is only true because of this ordering.
  - **Recovery is file-only, in both directions.** `/recover` and Settings → rotate both take the file; there is no typed-key fallback. The interstitial's gate is the checkbox alone — ticking "Save my recovery file" *is* the download (a tick is a valid user gesture, so the browser honours it), and Continue stays locked until then. Browser plumbing (download, file chooser, whole-window drop) is in `apps/client/src/lib/auth/recovery-file.ts`; the shared picker is `lib/components/recovery-file-picker.tsx`. **No server change**: the file is only a carrier for a key string the wire contract already had.
  - **Rule R1 (load-bearing): the recovery envelope wraps `vaultKeyRaw` DIRECTLY, never `HKDF(PBKDF2(password))`.** That is what lets the password credential be rotated without destroying the recovery path — and what keeps a vault recoverable by the very key that just recovered it, indefinitely. Do not "simplify" the recovery wrap to derive from the password.
  - The recovery envelope is AAD-bound to its vault (`recoveryAad(vaultId)`), so it cannot be transplanted onto another vault's row. Password and device envelopes still carry no AAD — that gap is a P2 follow-up, not an oversight.
  - Server flow (`apps/server/src/endpoints/recovery.rs`): `challenge` (unauth, per-IP throttle + max 3 live rows/vault) → `unlock` (unauth, releases the opaque envelope, **no state change**, challenge not consumed) → `rewrap` (**the only irreversible write**: CAS on `credential_version`, rotates the *password* credential, establishes the session) → `regenerate` (session-required, rotates the *recovery* key only, CAS on `recovery_verifier`).
  - **Every recovery failure returns one identical `401 AUTH_FAILED`.** Unknown selector, expired challenge, wrong proof, wrong vault, no recovery — deliberately indistinguishable, or each becomes an oracle. `GET /get_crypto_params` gains `recovery_salt` + `has_recovery` rather than adding a second unauthenticated params endpoint.
  - Three counters that must not be confused: `version` (document CAS for sync), `credential_version` (password-credential CAS), and `recovery_verifier` (recovery-rotation CAS). A rewrap bumps only the second — bumping `version` would invalidate every pending sync intent's `base_version`.
  - A failed proof **rolls the transaction back**, which undoes the challenge burn: the proof is a 256-bit MAC, so unlimited attempts against one challenge are not a brute-force surface, and a user who mistyped their key can simply retry. The challenge is single-use on the success path only.
  - The file is offered **once**, in a mandatory interstitial gated by a checkbox — no "remind me later", and Settings can only *rotate*, never replay it. `persistDeviceSecrets` runs only after that confirmation, so no vault ends up with a working device key but no saved recovery file. A Drive/cloud import **does not** mint a recovery key: the package carries the vault's recovery envelope (`recoveryEnvelope` in `apps/server/src/cloud/package.rs` and `apps/client/src/lib/state/type.ts`), so a restore registers those exact values and the file saved at creation keeps working on the new server. One vault id ⇒ one recovery key, on every instance; `PACKAGE_FORMAT_VERSION` is 2 for this reason.
  - The `ChallengeThrottle` is app-scoped `web::Data` constructed **once outside** the `HttpServer::new` closure — that closure runs per worker, so constructing it inside hands each worker its own budget.
- Client sync uses an offline-first `intent` table (durable encrypted mutation log: `operation` `create|update|delete`, `payload/payload_iv`, `device_id` per-vault, `base_version`, `synced`, `error`) with deterministic version-based conflict resolution — see `apps/client/conflict-resolution.md` and `architecture.md` before touching sync code. Merge policy `src/lib/sync/merge.ts:24` (idempotent create, LWW update, sticky delete, quarantine). Server CAS is `UPDATE … WHERE id=? AND version=?` + `rows_affected` → `409 VERSION_CONFLICT` (`src/endpoints/update_vault.rs:98`). Scheduler `src/lib/sync/sync-scheduler.ts` coalesces triggers (window-focus, online, intent-created, forced) but `useSyncTriggers` is currently disabled in `src/app/_layout.tsx:21`.
- Google Drive sync: bindings/tokens keyed by `vault_id` (`google_token`, `cloud_binding`). OAuth under `/api/google/*`; pending-state flow bypasses bootstrap auto-restore (`_layout.tsx:31`).

## Code Style

- Comment generously: explain operations and non-obvious logic, not every line. If code does something subtle (crypto steps, sync/conflict handling, SQL/OPFS quirks), say why in a comment.
- Log meaningfully: add logs for important events and state changes with correct severity levels (e.g. `error` for failures needing action, `warn` for recoverable anomalies, `info` for key lifecycle events). Don't log everything or noisy per-request details. Never log passwords, vault plaintext, `vault_verifier`, raw key bytes, or request bodies.

## Plans

When the user asks to "create a plan", "make a plan", "plan this", or otherwise explicitly requests a development plan:

- The plan MUST be written to a `.md` file in the repository.
- Prefer `plans/<descriptive-name>.md`.
- Create the `plans/` directory if necessary.
- Do not treat the chat response as the canonical copy of the plan.
- The Markdown file should contain the complete plan.
- Don't just transcribe the user's instructions into a plan: research the relevant code first, think through the approach, and proactively suggest alternatives or better ways to accomplish the goal (including trade-offs) before finalizing the plan.
- **Resolve every unknown before writing the file.** Once research is done, ask the user *all* remaining questions — use the `question` tool so options are easy to answer. Do not write the plan while any answer is still outstanding, and do not begin implementation with unresolved questions either.
- **No open questions in the plan doc.** Any uncertainty is settled with the user first and then recorded as a decided decision (with its rationale and the evidence that drove it), not parked as a TODO. A plan must be executable by someone who has no access to this conversation — if it needs a decision to proceed, the decision belongs in the question round, not in a trailing "Open questions" section.

### Plan Style

The taste every plan should aim for:

- Research-first: read the code and docs the plan touches (`architecture.md`, `conflict-resolution.md`, roadmap) before writing. Cite evidence as `file:line` so claims are checkable.
- Alternatives with verdicts: name the approaches considered, give each an honest trade-off, and recommend one explicitly. Rejected options stay in the plan with the reason (prevents re-litigation).
- Concrete over abstract: a files-to-touch index (new / edit / do-not-touch), exact endpoint/payload shapes, and real function/module names — never "update the backend accordingly".
- Trust-boundary aware: state what the change must NOT break (zero-knowledge invariants, session semantics, per-vault namespacing) and call out new attack surface with mitigations.
- No compat baggage by default: this project has no releases — change schemas in place, no version fields, no migrations, no legacy fallbacks, unless the user explicitly asks for backward compatibility.
- No new dependencies without justification: prefer owning small, auditable scripts over unmaintained third-party packages, especially on security-sensitive paths.
- No open questions section: every decision is settled with the user before the plan is written, then recorded in the plan as a decided choice with its rationale. Genuinely unknowable facts (an external API's undocumented limit) are stated as an explicit assumption plus the fallback the code takes when the assumption is wrong — never as a question.

### Phases

Break implementation into ordered phases (`M0` foundations/pipeline first, then feature slices, hardening/store-readiness last). Each phase states its scope plus acceptance criteria concrete enough to verify by hand (what to click, what to observe, what must fail cleanly). Phases are the agent's execution order — each one must leave the tree working.
